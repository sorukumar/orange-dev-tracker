# Governance & Research Layer: Data Logic

This document defines the data structures and forensic metrics used in the **BIP Sandbox** and the **Governance Analysis Pipeline**. These files reside in `data/governance/` and are generated by the scripts in `code/governance/`.

---

## 🏗 Data Manifest

### 1. `data/governance/bips_enriched.parquet`
The primary ledger for Bitcoin Improvement Proposals (BIPs). It is a "Forensic" dataset—bridging the spec (the BIP text) with real-world technical and social activity.

| Column | Metric | Description |
| :--- | :--- | :--- |
| `bip_id` | Identity | The unique identifier (e.g., "141"). Unique key. |
| `status` | Lifecycle | Formal status from the BIP header (Draft, Final, Deployed). |
| `revision_count` | **Technical Friction** | Number of unique git commits made to the BIP document in the `bitcoin/bips` repo. |
| `social_mention_count` | **Social Proof** | Number of unique discussion threads in the Mailing List/Delving Bitcoin mentioning this BIP. |
| `code_mention_count` | **Implementation Sync** | Count of commits in the `bitcoin/bitcoin` repository that reference this BIP ID. |
| `maturity_score` | **Vetting Level** | Calculated composite score: `(Revisions * 0.4) + (Social Mentions * 0.6)`. Normalized 0.0 - 1.0. |
| `theme` | Taxonomy | Thematic categorization (e.g., Consensus, Privacy) derived from regex scanning of Title and Content. |

### 2. `data/governance/social.parquet`
A unified archive of technical discussions across platforms.

| Column | Description |
| :--- | :--- |
| `source` | `mailing_list` or `delving_bitcoin`. |
| `canonical_id` | Identity mapped to the project's master `aliases_lookup.json`. |
| `thread_id` | Identifier used to group related messages into technical debates. |
| `link` | Persistent URL to the raw archive for deep forensic verification. |

### 3. `data/governance/expertise.json`
A derived artifact mapping human authority across the project.

*   **Full-Stack Architects**: Contributors who satisfy the "spec-to-code" loop. They have both authored a BIP and submitted production C++ code.
*   **Gatekeepers**: The most active participants in technical discussion. These individuals act as the "Social Filter" for new protocol research.

---

## 🧠 Metric Definitions & Rationale

### 1. Technical Friction (`revision_count`)
**Rationale:** In a consensus-driven project, a high number of revisions to a specification document isn't just "editing"—it's a proxy for technical complexity and the surfacing of edge cases.
*   *Interpretation*: A BIP with 100+ revisions (like BIP 341/Taproot) has undergone extreme forensic scrutiny compared to a BIP with 5 revisions.

### 2. Social Proof (`social_mention_count`)
**Rationale:** Bitcoin has no "Project Manager." Consensus is manufactured in technical forums. 
*   *Interpretation*: If a BIP has high "Friction" but zero "Social Proof," it is likely siloed research. If it has both, it is a high-consensus, high-impact effort.

### 3. The "Expertise" Join
We link `author_canonical_ids` from the BIPs with `canonical_id` from the Core commits to bridge the "Intellectual Center" of the project. This allows us to see if the people proposing the rules are the same people writing the code.

## 🛠 Maintenance & Rebuilds

The governance pipeline is isolated from the core dashboard rebuild to allow for faster experimental iteration.
*   **Rebuild Trigger**: `python code/governance/process_governance.py`
